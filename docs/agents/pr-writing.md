# PR 与提交文字规范（去 AI 味）

> 适用范围：commit message、PR 标题与正文、代码注释、收尾回复、learn 记录。
> 生效日期：2026-09-20
> 配套：`.opencode/skills/change-workflow/SKILL.md`（gate 编排，本规范的挂载点）、`docs/agents/quality-gates.md`（完成判据）

## 一、为什么需要这份规范

agent 产出的文字有可识别的模式，读者管它们叫 AI tells。一段 commit message 或 PR 正文被认出是模板腔之后，读者会连带怀疑内容本身。「测试通过」出现在这种上下文里，可信度跟着打折。

本规范把「去 AI 味」固化为提交前的固定动作。它是判断性要求，由 agent 按下文清单自查，不引入任何外部工具依赖。它与既有 commit 约定（Conventional Commits 前缀 + 中文标题）叠加生效，不替代它。

## 二、适用范围界定

只处理**本次写或改的文本**：

- 本次产出的 commit message、PR 标题与正文、收尾回复、learn 记录
- 本次变更中新增或修改的代码注释

不重写未触碰的既有 prose，旧文档和别人写的注释都不动。顺手大面积改写无关文本会污染 diff，违反 1 task = 1 ticket = 1 分支 = 1 PR 的垂直切片原则。

机器可解析的部分不在润色范围内：Conventional Commits 前缀、`fixes #N` / `Refs #N`、PR 模板必填字段（impact / verification / risk）的字段名。润色只作用于这些结构里的自然语言内容。

## 三、AI tells 清单

每条按「症状 / 反例 / 正例」给出。反例故意带着被点名的毛病，不要照着写。清单不求穷尽，命中表外的新痕迹时按同一原则处理。

### T1 浮夸（puffery）

症状：用「里程碑」「奠定基础」「标志着」「极大地」拔高事件，而不陈述发生了什么。事实和数字比形容词有力。

反例：`fix(editor): 本次修复标志着编辑器稳定性的重大里程碑，为后续迭代奠定了坚实基础`

正例：`fix(editor): 修复块删除后光标跳到文档开头的问题（#142）`

### T2 em dash 滥用

症状：一句话里插一个或多个破折号（— 或 ——）做停顿或补充。需要断开就拆句或用逗号；拿括号当替代品只是换一种痕迹。

反例：`这个方案——经过三轮评审——最终覆盖了全部已知场景。`

正例：`这个方案经过三轮评审，覆盖了全部已知场景。`

### T3 bold 滥用

症状：专有名词、关键词、每段首句都加粗。重点太多等于没有重点。

反例：`本次修改了 **渲染层** 的 **缓存策略**，并同步更新了 **CI 配置**。`

正例：`本次修改了渲染层的缓存策略，并同步更新了 CI 配置。`（一段最多粗一处真正要强调的）

### T4 被动语态

症状：「被修复」「已被验证」「由脚本完成」。执行者被藏起来，读者无法追责。执行者确实不明或无关紧要时才允许被动。

反例：`该缺陷已被修复，回归测试已被补充。`

正例：`我修复了该缺陷，补了两条回归测试。`

### T5 抽象隐喻名词

症状：substrate、wedge、vector、paradigm、north star、flywheel 这类词看着技术，其实没有具体所指；中文对应「赋能」「抓手」「底座」「飞轮」。换成机制的真实名字。

反例：`本工具包为变更管理提供了坚实的底座与自动化飞轮。`

正例：`本工具包用 5 个 gate 和 1 个自愈回路约束变更流程。`

### T6 规则三（硬凑三件套）

症状：什么都凑成三条，「更快、更强、更稳」。自然数量是几就写几，两件事就写两件。

反例：`这次重构让代码更清晰、更健壮、更易维护。`

正例：`这次重构删掉了 400 行重复代码，构建时间少了一半。`

### T7 聊天腔

症状：「希望这能帮到你」「当然可以」「请随时告诉我」。收尾回复和 PR 评论里最常见。

反例：`希望这个修复对你有帮助！如果还有问题请随时告诉我！`

正例：`修复已合并，#142 的复现步骤在 PR 描述里。`

### T8 Not just X but Y 句式

症状：「这不只是 X，更是 Y」。绕一圈抬高，信息量为零。直接说点本身。

反例：`这不只是一次依赖升级，更是对构建体系的重塑。`

正例：`升级到 TypeScript 5.6，构建报错从 31 个降到 0。`

### T9 模糊归因

症状：「专家认为」「业界普遍共识」「有研究表明」却不给出处。learn 记录里出现时危害最大，后续会话会把它当事实引用。给出处；给不出就删。

反例：`业界普遍认为 squash merge 更适合本项目。`

正例：`采用 squash merge，依据是 CONTRIBUTING.md 里的合并约定。`

### T10 同义词轮换

症状：同一段里换着叫同一个东西：「该函数」「此方法」「上述例程」，读者以为在说三件事。选定一个名字，重复它。

反例：`该函数解析配置，此方法随后校验，上述例程最后落盘。`

正例：`parse() 解析配置，随后校验，最后落盘。`

### T11 填充短语

症状：「值得注意的是」「需要指出的是」「众所周知」。删掉不损失任何信息。

反例：`值得注意的是，该接口在并发场景下非线程安全。`

正例：`该接口在并发场景下非线程安全。`

### T12 空泛结论

症状：「未来可期」「整体运行良好」「效果显著」。没有可验证的内容。换成数字或具体事实。

反例：`总体来看本次重构效果显著，后续表现值得期待。`

正例：`重构后冷启动从 3.2s 降到 1.1s。`

## 四、两遍扫描法

第一遍在写前，对草稿跑四步循环：

1. scan：按第三节清单逐条扫，标出命中的 tells
2. rewrite：逐条改写，保持原意，匹配目标语气（commit 标题要简洁，PR 正文要完整）
3. add soul：按第五节给文字加人味
4. self-audit：问一句「哪句话让人一眼看出是 AI 写的」，改掉剩下的痕迹；还有就回到第 1 步

第二遍在写后。提交、创建 PR、发送回复之前，把本次新增或改动的句子再扫一遍。理由很实际：第一遍之后往往还有编辑，补验证结果、改标题，新写的句子会带进新的 tells。第二遍不必重读全文，只扫增量。

## 五、add soul

去掉 tells 只完成一半，干净但没有声音的文字同样一眼假。

- 有立场。对事实做出反应，别中立罗列正反两面。「方案能用，但我不喜欢它」比「方案各有优劣」可信。
- 节奏变化。短句。然后来一个从容的长句。等长的句子排在一起像机器输出。
- 承认复杂。「结果不错，但过程比预想的乱」比单说「结果不错」真实。
- 用「我」。第一人称不丢人，收尾回复和 learn 记录里尤其该用。
- 留点乱。完美对称的结构看起来是机器做的，PR 正文不必每节等长。
- 具体而非空泛。不写「存在性能隐患」，写「p95 从 200ms 涨到 9s」。

## 六、挂载点

| gate | 文字产出点 | 动作 |
|---|---|---|
| G2 | `pr-automation.sh` 收口前的 commit message | 调脚本前完成两遍扫描（脚本直接 commit 并 push，事后改 message 只能 amend + force-push） |
| G2 | PR 创建后的标题与正文 | 创建后立即扫，发现问题用 `gh pr edit` 修正 |
| G3 | learn 记录 | 写入前扫；T9 模糊归因在这里危害最大 |
| G3 | 收尾回复 | 发送前扫 |
| G4 | 关闭 spec issue 的收口评论 | `gh issue close --comment` 前扫 |

## 七、边界：润色不改事实

**文字润色只改表达，不改技术结论。** 改写过程中若发现正文与代码事实不符（正文写「新增 3 条测试」而 diff 里只有 2 条），先修事实：或改正文，或补代码，事实修完再润色。润色在任何情况下都不是改事实的许可，数字与结论都不许动。

「测试通过」「已修复」这类结论的采信标准由 `quality-gates.md` 的 QG-5（独立验证 + 原始证据）约束。本规范不重复该判据，只管这些结论被写出来时的语言质量。
