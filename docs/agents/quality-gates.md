# 开发与测试质量门禁（QG / DQ）

> 适用范围：一切面向用户的 change / 缺陷修复，从 G0 拆票到 G2 合并、从缺陷填报到关闭的全流程质量校验。
> 生效日期：2026-09-20
> 配套：`docs/agents/task-tracking.md`（任务跟踪）、`docs/agents/defect-workflow.md`（缺陷流程）、`.opencode/skills/change-workflow/SKILL.md`（G0-G4 gate 编排——本文件的挂载点）

本文件含**两组**门禁：

| 组 | 覆盖 | 条目 |
|----|------|------|
| **QG** | 变更开发与测试（change 侧） | QG-1..QG-7（§二） |
| **DQ** | 缺陷处理（defect 侧） | DQ-1..DQ-8（§三） |

---

## 一、背景

一次真实交付失败促成本规范：某 change 的 9 个 PR 中，**8 个对 `<APP_DIR>/src` 零改动、对 e2e 零改动**，整个 change 期间新增 e2e 为 0。12 张票全部打勾，typecheck / lint / 单测 / CI **全绿**——而用户打开页面**看不到任何变化**。

随后的缺陷修复阶段又暴露**缺陷处理过程自身**的问题：修复期出现的 4 个「自测全绿但实际无效」交付全部由独立探针抓出（4/4，零例外）；一张缺陷票（`#187`）**全程未经 triage 就被修复**；一张缺陷票的**「修复方向」与真实根因不符**（票面指向「拆分下载预算」，实测真根因是陈旧断言）。

两侧的根因是同一个：**判据写在了「我方声称」而非「他方可观测」**。

- 变更侧：**「完成」的定义写在了库层而非用户层**，且没有任何门禁对此提出异议。
- 缺陷侧：**缺陷票的「修复方向」被当作结论而非假设**，且 triage 这一唯一质量入口**可被静默跳过**。

## 二、变更开发质量门禁（QG-1..QG-7）

### QG-1 用户层 AC 强制

**规则**：一切面向用户的票，其 AC 必须包含至少一条**浏览器可观测陈述**（格式见 §四）。

**理由**：该 change 的 AC 写作「读取函数返回块数组，4 条单测通过」「接口已导出，类型检查通过」——全部可在**库层**满足。于是实施者用最省力的方式满足 AC：写模块 + 写单测，从不触碰应用入口。**这不是偷懒，是 AC 允许这么做。**

**实证案例**：AC「`getBlocks()` 返回块数组，4 条单测通过」→ 库层可满足，用户层不可见 → 12 张票全部打勾而应用零变化。

**如何验证**：
```bash
gh issue view <票号> --json body --jq .body | grep -E "打开.*页面|dev server|\.spec\.ts"
# 无输出 = 违规
```

---

### QG-2 e2e 绑定

**规则**：用户可见变更**必须**新增或扩展 `<E2E_DIR>/*.spec.ts`；否则须在票上显式标注 `no-ui-impact`。

**理由**：CI 确实跑 e2e，但该 change 期间**新增 e2e 为 0**——套件覆盖的是**旧行为**。于是「CI 绿」只等于「旧功能没坏」，与「新功能存在」**逻辑上无关**。绿色提供了**虚假信心**。

**加这条不增加基建成本**：CI 已经在跑 e2e（见 `.change-workflow.conf` 的 `CMD_E2E`），只是让覆盖跟上新功能。

**实证案例**：9 个 change PR 中 8 个对测试目录改动为 0；其中「语义编辑态」（11 个功能的核心）零 e2e。

**如何验证**：
```bash
git diff --name-only origin/main...<分支> | grep "\.spec\.ts"
# 无输出且票上无 no-ui-impact 标注 = 违规
```

---

### QG-3 接线归属

**规则**：任何导出新 API 的票，必须显式指定「接线由哪张票负责」，并在该票 AC 中写出**具体接线位置**（应用入口 / 组件挂载点 / 命令注册处）。

**理由**：接线工作（注册扩展、挂载面板、注册命令）**不属于任何一张票的 AC** 时，在并行执行中**必然消失**——它是涌现属性，不是任何人的交付物。

**实证案例**：注册 7 个编辑器扩展、把结构面板挂进左栏、把命令注册进命令面板——这些在 12 张票全部完成后**根本没被做**，直到用户实测才发现。

**如何验证**：
```bash
git diff origin/main...<分支> -- <库入口文件> | grep "^+export"
grep -rn "<新导出名>" <APP_DIR>/src/ || echo "无引用 → 必须指定接线票"
```

---

### QG-4 真实路径测试

**规则**：测试必须驱动**真实链路**；禁止绕过 keymap / 事件 / 公共 API 直接调内部函数。测 DOM 可见性必须断言**计算样式**，禁止断言「元素存在」。测插件扩展必须经**真实 `EditorView`**，禁止 mock `EditorState`。

**理由**：绕过真实路径的测试会**全绿而功能为零**——因为 bug 恰好落在被绕过的那几跳里。

**实证案例**：某票的测试写作 `handleAutoPair(view, '**')` 直接传参调用，绕过 `keydown → keymap → inputHandler` **两跳**。而 bug 恰在那两跳：`key: '**'` 是**非法键名，被静默丢弃**。测试全绿，真实按键**零配对**。

**补充反例**：某 e2e 规格用 `record()` 吞掉步骤断言失败以保证后续步骤继续执行，导致**步骤全挂时测试仍然「绿」**——而 CI 只看退出码。**该 spec 长期失去守门能力**。凡「吞异常以延续执行」的测试，必须把累积失败在测试末尾升级为测试失败。

**如何验证**：review 时逐条读测试，确认断言落在公共入口。正反例见 §五。

---

### QG-5 独立验证 + 原始证据

**规则**：每个任务的完成声明，必须附**验证者自己的探针的原始输出**。未粘贴原始观察证据的「已完成」**不予采信**。

**理由**：自证无效。修复期抓出 **4 个「自测全绿但实际无效」**的交付，**4/4 全部由独立探针抓出，零例外**。

**实证案例（全部为自报「已通过」）**：

| 对象 | 自报 | 独立探针实测 |
|------|------|--------------|
| 自动配对 | 测试通过 | 绕过 keymap，真实按键零配对 |
| 有序列表 | 已修复 | 引入回归：数字消失 + 圆点覆盖任务标记 |
| 结构面板 | 浏览器冒烟通过 | `useMemo([editorView])` 依赖稳定对象 → 诊断**永不刷新** |
| 测试统计 | 408 passed | 残留半成品文件未被计数，**误报为绿** |

**探针类型清单**：真实按键（驱动输入管线）/ 真实 DOM 计算样式（`getComputedStyle`）/ 真实 XML 解析 / 真实 `EditorView`。

**成本**：本地 e2e 单文件实测约 **16 秒**，成本极低，收益是拦截**最昂贵的缺陷类型**（功能不存在）。

**如何验证**：票上是否有验证者粘贴的原始输出块（非实施者的测试摘要）。

---

### QG-6 集成 checkpoint

**规则**：change 票数 ≥ 6 时，每完成 **≤ 4 票**必须插入一次集成 checkpoint：合并到集成分支 → 构建 → **浏览器打开一次** → 记录「现在用户能看到什么」。

**理由**：多分支并行 + 延迟集成，反复 rebase 使 barrel 文件冲突解决退化为**机械粘贴 export**。「合并」只意味着 git 层面成功，**从未意味着应用能跑**。

**实证案例**：12 张票各自分支 → 反复 rebase → barrel 冲突 → 机械粘贴 export → 从未真正合并运行。

**如何验证**：change 的 checkpoint 记录（每 ≤4 票一条「用户现在能看到什么」的观察记录）。

---

### QG-7 纵向切片

**规则**：G0 拆票时，每条 task 必须满足**纵向切片**——贯穿 schema→API→UI→test 全层、独立可演示可验证。判据：**一张票做完，用户能否看到点东西？不能 → 切错了。**

**理由**：横向（按层）切片下，每层「完成」时**不产生任何用户价值**；层与层之间的接线无人负责；N 张票做完才第一次具备「可用」的可能，而那一刻没人去测。

**实证案例**：12 张票按架构层横切——块模型 → 装饰引擎 → 命令注册表 → AI Provider → 章节树 → 工具栏。每层单独「完成」时用户看到的是**零**。

**如何验证**：反向验收判据——若一条 AC 能在**不修改 `<APP_DIR>`** 的前提下被满足，说明票切错了。

## 三、缺陷处理质量门禁（DQ-1..DQ-8）

> 缺陷侧的核心失效模式是：**票面的「修复方向」被当作结论**，且 **triage 可被静默跳过**。

### DQ-1 triage 不可跳过

**规则**：任何缺陷票在开工修复前，必须完成 triage：移除 `needs-triage`、加上 `ready-for-agent`、**票上必须存在 triage brief 评论**（含「已核实」结论 + Agent Brief）。三者缺一即**禁止开工**。

**理由**：triage 是缺陷流程唯一的质量入口。跳过后，票面的假设无人核对，直接进入实施。

**实证案例**：`#187` 全程**仅有 `needs-triage`、无 `ready-for-agent`、评论数 0**——即从未 triage——却被直接修复并合并。对照同批其他票均有「## Triage 结论 + ## Agent Brief」评论，说明流程本身可用，只是**无门禁强制**。

**如何验证**：
```bash
gh issue view <N> --json labels,comments \
  --jq '{labels: [.labels[].name], hasBrief: ([.comments[].body] | map(select(test("Triage 结论|Agent Brief"))) | length > 0)}'
# 期望：labels 不含 needs-triage、含 ready-for-agent、hasBrief = true
```

---

### DQ-2 根因须独立确认，票面「修复方向」仅供参考

**规则**：票面写的「修复方向 / 建议方案」是**假设，不是结论**。修复前必须**独立复现并定位根因**；若实际根因与票面假设不符，**必须在票上更正**（记录实际根因与票面偏差）。

**理由**：缺陷票由发现者撰写，其诊断受限于当时的观察角度。把假设当结论会导致「按票面改了但没修好」或「改错地方」。

**实证案例**：`#187` 票面「修复方向（待排查确认，此处不定案）」写「**拆分巨型旅程**（首要）」，理由是「4 个串行下载等待的最坏情况和 = 整个测试预算」。独立探针实测真根因是**测试步骤的陈旧断言**各烧 10-15s 把预算推到边界——这既解释了「间歇」，也说明票面的「预算不足」解释是**片面的**。若按票面只做拆分而不修陈旧断言，超时会**依旧复现**。

**如何验证**：修复 PR 的 body 是否含「实际根因 vs 票面假设」的对照；不一致时票上是否有更正评论。

---

### DQ-3 先红后绿（复现证据强制）

**规则**：修复前**必须先有可复现的失败证据**（失败的测试原始输出 / 探针原始输出），并作为「红」粘贴到票上。未附「红」证据的修复**不予合并**。

**理由**：没有「红」就无法证明「绿」是修复而非巧合；也无法证明修的是同一个问题。

**实证案例**：修复期多张票直接改代码，验证在事后补做。某票首版「修复」实际**引入回归**（有序列表数字消失 + 圆点覆盖任务标记）——若有先行的红/绿对照，该回归会在同一轮暴露。

**如何验证**：票上是否有修复前的失败输出（红）与修复后的通过输出（绿）成对出现。

---

### DQ-4 「flaky」必须给出机制解释，不得以重跑结案

**规则**：将失败判为「flaky」时，**必须给出「为何间歇」的机制解释**，而不能以「重跑通过」结案。特别地：**若测试吞掉断言失败（继续执行模式），flaky 可能掩盖确定性损坏**，此时必须逐步核对每个子步骤的结论。

**理由**：重跑通过只证明「这次没踩到」，不证明「行为正确」。若某失败的概率较高但非 100%，重跑会**系统性地放过**真实缺陷。

**实证案例**：`#187` 以「CI flaky，跨 PR 间歇复现」立项并长期挂着。真相是：测试步骤是**确定性失败**（陈旧断言必失败），它们吃掉约 25s 预算，使总时长落在边界区间 —— **恰好跨过超时线**，于是表现为「间歇」。**「flaky」这个标签主动掩盖了一个必然损坏的 spec**；且该 spec 用 `record()` 吞掉步骤失败，CI 只看退出码 → 步骤全挂也绿。

**如何验证**：flaky 票是否有机制解释段落；是否有「逐步核对各子步骤结论」而非仅「重跑 N 次通过」的证据。

---

### DQ-5 关闭缺陷须附验证者原始证据

**规则**：关闭缺陷票前，必须由**验证者（非修复者）**跑自己的探针，并把**原始输出**粘贴到票上。「测试通过」「已修复」「冒烟正常」是**结论不是证据**，不予采信。

**理由**：同 QG-5。缺陷场景下更严——因为「已修复」正是假修复的自报措辞。

**实证案例**：4 个假修复全部以「测试通过 / 已修复 / 冒烟通过 / 计数通过」自报完成，**4/4 全部由独立探针推翻**。

**如何验证**：票上是否存在验证者粘贴的原始输出块（标准输出 / DOM 快照 / 计算样式值 / 解析错误数）。

---

### DQ-6 同根因合并例外（1 bug = 1 PR 的合法豁免）

**规则**：默认 **1 bug 票 = 1 `fix/<slug>` 分支 = 1 PR**。**例外**：若 N 张票**同根因、同文件、同修复**，允许 1 PR 关闭 N 票——但 PR body 必须**逐票 `fixes #N`** 并**说明共同根因**，且各票需在评论中记录「已由 #PR 一并修复」。

**理由**：规则被合理违反时若没有豁免通道，执行者会**静默忽略规则**，从而侵蚀整条规则（含其真正该守的默认情形）。

**实证案例**：4 张同属「智能输入」、同一根因、同一文件的票由 1 个 PR 一并关闭。这是**合理**的，但规则现文无任何豁免条款——属于「规则与现实不符」。

**如何验证**：PR body 是否逐票 `fixes #N`；是否说明共同根因。

---

### DQ-7 多票同根因 → 必须升级为规范修订

**规则**：当 **≥3 张缺陷票**指向**同一流程环节**时，不得只逐票修复，必须**反查该流程环节并产出规范修订**（QG / DQ 条目或流程文档），在 change 或缺陷票上留痕。

**理由**：多票同源意味着缺陷来自**流程而非个体实现**。只修个例，同类问题会在下一个 change 复现。

**实证案例**：某 change 的 10 张缺陷票**全部**指向同一流程环节——「完成定义写在库层 + 无 e2e 绑定 + 接线无归属」。当时逐票修复（6 个 PR），**从未反查流程**，直到用户要求复盘才产出 QG-1..QG-7。若在**第 3 张票**时就反查，可提前拦截后续 7 张。

**如何验证**：是否产出了规范修订并能回溯到触发它的缺陷集合。

---

### DQ-8 生命周期标签维护

**规则**：缺陷票关闭时**必须移除进度类标签**（`needs-triage` / `ready-for-agent`），使标签与终态一致。P0/P1 票**部分交付**时，票**保持 OPEN** 并在票上评论**列出已交付增量与剩余项**。

**理由**：标签即状态机。关闭票残留 `ready-for-agent` 会污染 frontier 查询（`gh issue list --label ready-for-agent --state open`），而该查询正是 G3 自动推进的依据。

**实证案例**：一张 P0 票在子集交付后仍 `OPEN` 且带 `ready-for-agent`，与已关闭的同批票（同样残留该标签）混在同一标签集中；剩余增量仅靠人工评论记录。

**如何验证**：
```bash
gh issue list --label ready-for-agent --state all --json number,state \
  --jq '.[] | select(.state=="CLOSED") | .number'
# 期望：无输出（关闭票不应残留 ready-for-agent）
```

## 四、QG-1 的固定 AC 格式

面向用户的票，AC 必须包含如下格式的条目（可直接复制，`<dev 命令>` 取 `.change-workflow.conf` 的 `CMD_*`）：

```
在 `<dev 命令>` 打开的页面中，
<具体操作> 之后，<可具体观测的结果>。
验证：<E2E_DIR>/<feature>.spec.ts 通过。
```

**反向验收判据**：若一条 AC 能在**不修改 `<APP_DIR>`** 的前提下被满足 → 说明票切错了（触发 QG-7）。

## 五、QG-4 的代码对照

```ts
// ❌ 绕过 keymap 两跳，bug 恰好在那两跳
handleAutoPair(view, '**')

// ✅ 驱动真实输入路径
await view.dispatch(inputEvent(view, '**'))
```

同源补充规则：

- 测 DOM 可见性 → 必须断言**计算样式**，禁止断言「元素存在」
  ```ts
  // ❌ 元素存在即通过，但可能 opacity:0 不可见
  await expect(marker).toHaveCount(1)
  // ✅ 断言真实可见性
  expect(Number(await marker.evaluate((el) => getComputedStyle(el).opacity))).toBe(0)
  ```
- 测插件扩展 → 必须经**真实 `EditorView`**，禁止 mock `EditorState`
  - 依赖语法树解析的逻辑（如结构诊断）无法被 mock 对象满足，必须用真实实例
- **吞异常的测试（继续执行模式）** → 必须把累积失败在测试末尾**升级为测试失败**，否则 CI 退出码与测试结论脱钩
  ```ts
  // ❌ record() 吞掉断言失败以延续后续步骤 → 步骤全挂时测试仍「绿」，CI 只看退出码
  const record = async (name, fn) => { try { await fn() } catch (e) { steps[name] = { pass: false } } }
  // ✅ 末尾把累积失败升级为测试失败，使退出码与结论一致
  expect(Object.entries(steps).filter(([, s]) => !s.pass).map(([n]) => n)).toEqual([])
  ```

## 六、QG-5 的独立验证协议

验证者（orchestrator，非实施者）必须执行：

1. 读**实际 diff**，不只读报告
2. 跑**自己的探针**（不复用实施者的测试）
3. **把原始输出粘贴到票上**（原始 stdout / DOM 快照 / 计算样式值 / 解析错误数）
4. 未粘贴原始观察证据的「已完成」→ **不予采信**

**禁止采信的证据形式**：「测试通过」「已修复」「冒烟正常」——这些是**结论**，不是**证据**。

| 门禁 | 可否豁免 | 条件 |
|------|----------|------|

| QG-3 接线归属 | ❌ | 不可豁免 |
| QG-4 真实路径测试 | ❌ | 不可豁免 |
| QG-5 独立验证 | ❌ | 不可豁免 |
| QG-6 集成 checkpoint | ✅ | 票数 < 6 时自然不适用 |
| QG-7 纵向切片 | ❌ | 不可豁免 |
| DQ-1 triage 不可跳过 | ❌ | 不可豁免 |
| DQ-2 根因独立确认 | ❌ | 不可豁免 |
| DQ-3 先红后绿 | ❌ | 不可豁免（紧急 P0 可事后补，但须在票上留痕） |
| DQ-4 flaky 机制解释 | ❌ | 不可豁免 |
| DQ-5 关闭附原始证据 | ❌ | 不可豁免 |
