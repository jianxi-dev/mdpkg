# 开发与测试质量门禁（QG / DQ）

> 适用范围：一切面向用户的 change / 缺陷修复，从 G0 拆票到 G2 合并、从缺陷填报到关闭的全流程质量校验。
> 生效日期：2026-09-20
> 配套：`docs/agents/task-tracking.md`（任务跟踪）、`docs/agents/defect-workflow.md`（缺陷流程）、`.opencode/skills/change-workflow/SKILL.md`（G0-G4 gate 编排——本文件的挂载点）

本文件含**两组**门禁：

| 组 | 覆盖 | 条目 |
|----|------|------|
| **QG** | 变更开发与测试（change 侧） | QG-1..QG-8（§二） |
| **DQ** | 缺陷处理（defect 侧） | DQ-1..DQ-8（§三） |

---

## 一、背景

一次真实交付失败促成本规范：某 change 的 9 个 PR 中，**8 个对 `<APP_DIR>/src` 零改动、对 e2e 零改动**，整个 change 期间新增 e2e 为 0。12 张票全部打勾，typecheck / lint / 单测 / CI **全绿**——而用户打开页面**看不到任何变化**。

随后的缺陷修复阶段又暴露**缺陷处理过程自身**的问题：修复期出现的 4 个「自测全绿但实际无效」交付全部由独立探针抓出（4/4，零例外）；一张缺陷票（`#187`）**全程未经 triage 就被修复**；一张缺陷票的**「修复方向」与真实根因不符**（票面指向「拆分下载预算」，实测真根因是陈旧断言）。

两侧的根因是同一个：**判据写在了「我方声称」而非「他方可观测」**。

- 变更侧：**「完成」的定义写在了库层而非用户层**，且没有任何门禁对此提出异议。
- 缺陷侧：**缺陷票的「修复方向」被当作结论而非假设**，且 triage 这一唯一质量入口**可被静默跳过**。

## 二、变更开发质量门禁（QG-1..QG-8）

### 规格双形态与验收锚点（QG-1 前置定义）

**规则**：每个 change 的规格必须同时产出**双形态**并**双向链接**：

- **人读层**（主产物，不可丢）：proposal / design / AC / Scenario 的自然语言叙述，承载意图、理由与验收语义。
- **机读层**（`conformance.json` 锚点集）：每条锚点含**具体期望值**、**来源**、**断言类型**（`exact | state-machine | perceptual`）。

人读条目 MUST 携带锚点引用；锚点 MUST 回指存在的人读条目。G0 机检四项：**完备性**（每 requirement ≥1 anchor）/ **无孤儿**（anchor 回指存在 requirement）/ **可断言性**（`assert` 非空且含具体值 token：数字 / 引号串 / `#hex` / 状态迁移关键词）/ **来源非空**。规范性需求见能力 `mechanized-quality-gates`。

**理由**：纯机读丢意图、不可评审；纯散文不可核验（v1.9.0 的失败：规格只有散文形态、无机制强制 → 「门禁有定义、无机器强制、靠自证」）。双形态 + 链接 = 可读**且**可核验；「链接完整性」本身可机检。

**实证案例**：v1.9.0 把保真/生命周期门禁写进定义层（文字 + SKILL 指令），24 小时后被消费仓证伪——该 change 16/16 勾选、CI 全绿、已归档，用户打开即见约 20 处与原型不符；根因是规格无锚点、门禁无强制。

**如何验证**：
```bash
# G0 锚点门（cw-tickets-check.sh C3/C4 conformance 机检）：
./scripts/cw-tickets-check.sh --change <名>
# 退 0 = 完备/无孤儿/可断言/来源非空；退 1 = 违规（缺锚点 / 孤儿 / 不可断言 / 来源缺失）
# 人读层不可丢：规格须保留可读叙述，机读制品不得取代它
# G0 一致性制品生成与校验：
./scripts/cw-conformance.sh generate <change>   # 解析 anchors.md → 四规则校验 → 写 conformance.json
./scripts/cw-conformance.sh lock <change>       # 对 conformance.json + baseline/*.png 逐文件 sha256 → 写 conformance.lock
./scripts/cw-conformance.sh verify <change>     # 重投影 anchors.md 语义比对 + lock 哈希核验
```

### QG-1 用户层 AC 强制（三分类：存在 / 生命周期 / 保真）

**规则**：一切面向用户的票，其 Acceptance Criteria 必须**同时**覆盖三类：

1. **存在**（存在性）：打开页面后出现 X
2. **生命周期**（交互闭环）：覆盖 `打开·切换·取消·外部点击·空态·关闭` 六态，并断言取消后无残留
3. **保真**（可判真伪）：可判真伪的文本/像素结果（如：卡片标头文本严格等于「注释」；fenced code 行不含反引号），而非「渲染正确」
4. **验收锚点**（机读）：每条 AC 必须携带至少一个验收锚点（`conformance.json` 的 `A-<n>.<m>`）；锚点须含**具体期望值 + 来源**，「渲染正确 / 功能可用」类无具体值、或来源缺失者不得成锚点

缺一即违规。锚点四项机检（完备 / 无孤儿 / 可断言 / 来源非空）见「规格双形态与验收锚点」与 `cw-tickets-check.sh`。

**理由**：该 change 的 AC 写作「读取函数返回块数组，4 条单测通过」「接口已导出，类型检查通过」——全部可在**库层**满足。于是实施者用最省力的方式满足 AC：写模块 + 写单测，从不触碰应用入口。**这不是偷懒，是 AC 允许这么做。** 实证：editor-v2 29/29 勾选、CI 全绿，用户仍见 D1–D10——callout 标题重复「注释 注释」、代码围栏残留反引号、斜杠菜单点外部不关、取消后 `/` 残留、表格点一下塌成裸源码、空态无「新建文档」入口、React 重复 key。根因在链条四层：**L-1 学习/需求输入无证据、L0 设计→规格翻译损耗、L3 断言停在「元素存在」、L4 验收用存在性自证**。三分类 AC 强制把「生命周期」与「保真」写进判据，堵住 L0/L3/L4。

**实证案例**：AC「`getBlocks()` 返回块数组，4 条单测通过」→ 库层可满足，用户层不可见 → 12 张票全部打勾而应用零变化。editor-v2 D2 callout「注释 注释」→ 仅存在性 AC 无法拦；D3 围栏 `\`js` → 无保真文本相等 AC 无法拦；D4/D6 菜单点外部不关/取消残留 `/` → 无生命周期 AC 无法拦。

**如何验证**：
```bash
gh issue view <票号> --json body --jq .body | grep -E "打开.*页面|dev server|\.spec\.ts"
# 无输出 = 违规
# 机检三分类关键词（cw-tickets-check.sh C3/C4）：
gh issue view <票号> --json body --jq .body | grep -E "取消|残留|空态|严格等于|不含"
# 无输出 = 违规
```

### QG-2 e2e 绑定

**规则**：用户可见变更**必须**新增或扩展 `<E2E_DIR>` 下的 e2e 用例；否则须在票上显式标注 `no-ui-impact`。

**理由**：CI 确实跑 e2e，但该 change 期间**新增 e2e 为 0**——套件覆盖的是**旧行为**。于是「CI 绿」只等于「旧功能没坏」，与「新功能存在」**逻辑上无关**。绿色提供了**虚假信心**。

**加这条不增加基建成本**：CI 已经在跑 e2e（见 `.change-workflow.conf` 的 `CMD_E2E`），只是让覆盖跟上新功能。

**实证案例**：9 个 change PR 中 8 个对测试目录改动为 0；其中「语义编辑态」（11 个功能的核心）零 e2e。

**如何验证**：
```bash
git diff --name-only origin/main...<分支> | grep "\.spec\.ts"
# 无输出且票上无 no-ui-impact 标注 = 违规
```

### QG-3 接线归属

**规则**：任何导出新 API 的票，必须显式指定「接线由哪张票负责」，并在该票 AC 中写出**具体接线位置**（应用入口 / 组件挂载点 / 命令注册处）。

**理由**：接线工作（注册扩展、挂载面板、注册命令）**不属于任何一张票的 AC** 时，在并行执行中**必然消失**——它是涌现属性，不是任何人的交付物。

**实证案例**：注册 7 个编辑器扩展、把结构面板挂进左栏、把命令注册进命令面板——这些在 12 张票全部完成后**根本没被做**，直到用户实测才发现。

**如何验证**：
```bash
git diff origin/main...<分支> -- <库入口文件> | grep "^+export"
grep -rn "<新导出名>" <APP_DIR>/src/ || echo "无引用 → 必须指定接线票"
```

### QG-4 真实路径测试 + 断言强度阶梯

**规则**：测试必须驱动**真实链路**；禁止绕过 keymap / 事件 / 公共 API 直接调内部函数。测 DOM 可见性必须断言**计算样式**，禁止断言「元素存在」。测插件扩展必须经**真实 `EditorView`**，禁止 mock `EditorState`。

**断言强度阶梯**（e2e 断言须落在尽可能高的层级）：

| 层级 | 断言形态 | 适用门槛 |
|---|---|---|
| 1 存在 | `toHaveCount(1)` | 仅用于确认挂载 |
| 2 可见 | 计算样式非隐藏（`getComputedStyle`） | 所有 UI 变更 |
| 3 文本相等 | `toHaveText` / `textContent` 严格等于 | **渲染 / 装饰 / 插入 / 浮层类变更至少到此级** |
| 4 状态往返 | 操作→反向→回初始（打开→取消→回初始） | **可取消 / 可关闭交互必须到此级** |
| 5 视觉 | 多态截图对比（状态覆盖矩阵 ≥4 态） | 关键交互流程 |

**CI 三层自动核验**（ui-surface 票强制，全自动无人）：实现提交后 CI 自动运行——

- **T1 确定量**：计算样式 / DOM 属性 / 文本 vs `conformance.json`，精确断言（色值 / 字阶 / 间距 4 倍数 / 图标名 / 几何 / 文案）。
- **T2 感知**：实现截图 vs `baseline` 的像素 / 感知 diff + 多模态结构化判定。
- **T3 状态机**：六态往返 + 无残留。

核验 MUST 在 CI 执行（断言已提交），MUST NOT 依赖人工观察。

**一致性制品与 baseline**：有原型的 change，G0 从原型结构化表**程序化生成**一致性制品（`conformance.json` + `baseline/*.png` + e2e 断言骨架）并**锁定哈希**；实现阶段 MUST 只消费、MUST NOT 篡改 baseline（哈希变即核验失败）。

**理由**：绕过真实路径的测试会**全绿而功能为零**——因为 bug 恰好落在被绕过的那几跳里。editor-v2 实证：D2 callout「注释 注释」→ 仅 `toHaveCount(1)` 无法拦，需文本相等；D4/D6 菜单点外部不关/取消残留 `/`→ 无状态往返断言无法拦。

**实证案例**：某票的测试写作 `handleAutoPair(view, '**')` 直接传参调用，绕过 `keydown → keymap → inputHandler` **两跳**。而 bug 恰在那两跳：`key: '**'` 是**非法键名，被静默丢弃**。测试全绿，真实按键**零配对**。

**补充反例**：某 e2e 规格用 `record()` 吞掉步骤断言失败以保证后续步骤继续执行，导致**步骤全挂时测试仍然「绿」**——而 CI 只看退出码。**该 spec 长期失去守门能力**。凡「吞异常以延续执行」的测试，必须把累积失败在测试末尾升级为测试失败。

**如何验证**：
```bash
# 真实路径：review 时逐条读测试，确认断言落在公共入口
# 断言阶梯机检：
git diff origin/main...<分支> -- '*.spec.ts' | grep -E "toHaveText|textContent|getComputedStyle"
# 无输出且为渲染/浮层/可取消类 = 违规
```

### QG-5 独立验证 + 原始证据 + 视觉探针

**规则**：每个任务的完成声明，必须附**验证者自己的探针的原始输出**。未粘贴原始观察证据的「已完成」**不予采信**。**收口（G2 合并 / G4 归档）须跑 `.change-workflow.conf` 的 `CMD_TEST` 全链，禁止只跑受影响的子集**——子集验证无法捕获跨模块回归（实证：#556 收口只跑 `test_qa_html_gates` 漏跑 `test_v2_matcher`，回归穿过收口门禁）。

**探针类型清单**（按优先级）：

1. **真实按键**（驱动输入管线）
2. **真实 DOM 计算样式**（`getComputedStyle`）
3. **真实 XML 解析**
4. **真实 `EditorView`**
5. **视觉探针**（关键态截图 + 多模态**自动**复核：跨模型家族投票，非人工）——**交互类 UI 变更强制**

**证据效力判据**：

- **「元素存在 / count>0」不是有效证据**——无法区分「可见」与「opacity:0 不可见」，无法捕获文本残留（如 callout 重复、围栏反引号、取消后 `/` 残留）
- **「同类探针自证」不算证据**——由与实现者同类的自动化探针报告「通过率」（如「91% 通过」）即为自证无效
- **禁止伪造手动 QA**——把「真机手动 QA」实现为自动化 spec（如 `qa-*.spec.ts`）是反模式（名字即矛盾）；手动 QA 必须是**真用一遍 + 逐步观察 + 截图 + 结论**

**验证分离机制化**：判者 ≠ 写者，靠**跨模型自动复核**（不同模型家族对同一 diff + 同一 baseline 独立判定，consensus 为高置信信号）；MUST NOT 将人工审批作为质量兜底。

**降级收紧**：`cw-evidence.sh` 降级（exit 3）MUST 附**机器可核验的理由**并记录（缺什么工具 / 环境探测输出），MUST NOT 默认放行；降级 MUST NOT 改变门禁判据。

**理由**：自证无效。修复期抓出 **4 个「自测全绿但实际无效」**的交付，**4/4 全部由独立探针抓出，零例外**。editor-v2 实证：D2–D6 均为「元素存在」级断言无法拦；D4/D6 需状态往返（视觉探针副产物）才能拦。

**实证案例（全部为自报「已通过」）**：

| 对象 | 自报 | 独立探针实测 |
|------|------|--------------|
| 自动配对 | 测试通过 | 绕过 keymap，真实按键零配对 |
| 有序列表 | 已修复 | 引入回归：数字消失 + 圆点覆盖任务标记 |
| 结构面板 | 浏览器冒烟通过 | `useMemo([editorView])` 依赖稳定对象 → 诊断**永不刷新** |
| 测试统计 | 408 passed | 残留半成品文件未被计数，**误报为绿** |

**成本**：本地 e2e 单文件实测约 **16 秒**，成本极低，收益是拦截**最昂贵的缺陷类型**（功能不存在）。

**如何验证**：票上是否有验证者粘贴的原始输出块（非实施者的测试摘要）。**机检视觉探针**：
```bash
# 状态覆盖矩阵机检（evidence-capture.md §3.2）：
ls .artifacts/<task>/state-coverage.json && jq '.states | length' .artifacts/<task>/state-coverage.json
# 态数 <4 = 违规
```

### QG-6 集成 checkpoint

**规则**：change 票数 ≥ 6 时，每完成 **≤ 4 票**必须插入一次集成 checkpoint：合并到集成分支 → 构建 → **浏览器打开一次** → 记录「现在用户能看到什么」。

**理由**：多分支并行 + 延迟集成，反复 rebase 使 barrel 文件冲突解决退化为**机械粘贴 export**。「合并」只意味着 git 层面成功，**从未意味着应用能跑**。

**实证案例**：12 张票各自分支 → 反复 rebase → barrel 冲突 → 机械粘贴 export → 从未真正合并运行。

**如何验证**：change 的 checkpoint 记录（每 ≤4 票一条「用户现在能看到什么」的观察记录）。

### QG-7 纵向切片

**规则**：G0 拆票时，每条 task 必须满足**纵向切片**——贯穿 schema→API→UI→test 全层、独立可演示可验证。判据：**一张票做完，用户能否看到点东西？不能 → 切错了。**

**理由**：横向（按层）切片下，每层「完成」时**不产生任何用户价值**；层与层之间的接线无人负责；N 张票做完才第一次具备「可用」的可能，而那一刻没人去测。

**实证案例**：12 张票按架构层横切——块模型 → 装饰引擎 → 命令注册表 → AI Provider → 章节树 → 工具栏。每层单独「完成」时用户看到的是**零**。

**如何验证**：反向验收判据——若一条 AC 能在**不修改 `<APP_DIR>`** 的前提下被满足，说明票切错了。

```bash
./scripts/cw-tickets-check.sh --change <名>
# 发布前机检：退 0 才允许发布子票；C3/C4 检查 AC 可观测形态与禁入信号，C8 检查粒度声明与票间 What 重叠
```

### QG-8 发现闭环门

**规则**：任何报告 / findings / 实测发现中记录的缺陷，必须转成 tracked issue 或规格条目，否则该 change **不得标记完成**。

**理由**：editor-v2 实测发现 D1–D10 中，**0 条转为 tracked issue**，全部以「已知问题」口头传递 → 下一 change 复发。发现闭环门把「发现→转票/入规格」强制为完成前置条件。

**实证案例**：editor-v2 实测 10 条缺陷（callout 重复、围栏反引号、菜单不关、取消残留、表格塌陷、空态无入口、React 重复 key 等），**零条**在 GitHub 上有对应 issue 或 spec 条目。若此门生效，每条缺陷须显式转票或入规格，下一 change 即可对账。

**如何验证**：
```bash
# findings 里的每条缺陷是否能追到 issue（缺陷条目数 vs issue 数）：
grep -cE "^\|.*(反馈|问题|缺陷)" docs/plans/*findings*.md
gh issue list --label bug --state all --json number --jq 'length'
# 不匹配 = 违规
```

## 三、缺陷处理质量门禁（DQ-1..DQ-8）

> 缺陷侧的核心失效模式是：**票面的「修复方向」被当作结论**，且 **triage 可被静默跳过**。

### DQ-1 triage 不可跳过

**规则**：任何缺陷票在开工修复前，必须完成 triage：移除 `needs-triage`、加上 `ready-for-agent`、**票上必须存在 triage brief 评论**（含「已核实」结论 + Agent Brief）。三者缺一即**禁止开工**。

**理由**：triage 是缺陷流程唯一的质量入口。跳过后，票面的假设无人核对，直接进入实施。

**实证案例**：`#187` 全程**仅有 `needs-triage`、无 `ready-for-agent`、评论数 0**——即从未 triage——却被直接修复并合并。对照同批其他票均有「## Triage 结论 + ## Agent Brief」评论，说明流程本身可用，只是**无门禁强制**。

**如何验证**：
```bash
gh issue view <N> --json labels,comments \
  --jq '{labels: [.labels[].name], hasBrief: ([.comments[].body] | map(select(test("Triage 结论|Agent Brief"))) | length > 0)}'
# 期望：labels 不含 needs-triage、含 ready-for-agent、hasBrief = true
```

---

### DQ-2 根因须独立确认，票面「修复方向」仅供参考

**规则**：票面写的「修复方向 / 建议方案」是**假设，不是结论**。修复前必须**独立复现并定位根因**；若实际根因与票面假设不符，**必须在票上更正**（记录实际根因与票面偏差）。

**理由**：缺陷票由发现者撰写，其诊断受限于当时的观察角度。把假设当结论会导致「按票面改了但没修好」或「改错地方」。

**实证案例**：`#187` 票面「修复方向（待排查确认，此处不定案）」写「**拆分巨型旅程**（首要）」，理由是「4 个串行下载等待的最坏情况和 = 整个测试预算」。独立探针实测真根因是**测试步骤的陈旧断言**各烧 10-15s 把预算推到边界——这既解释了「间歇」，也说明票面的「预算不足」解释是**片面的**。若按票面只做拆分而不修陈旧断言，超时会**依旧复现**。

**如何验证**：修复 PR 的 body 是否含「实际根因 vs 票面假设」的对照；不一致时票上是否有更正评论。

---

### DQ-3 先红后绿（复现证据强制）

**规则**：修复前**必须先有可复现的失败证据**（失败的测试原始输出 / 探针原始输出），并作为「红」粘贴到票上。未附「红」证据的修复**不予合并**。

**理由**：没有「红」就无法证明「绿」是修复而非巧合；也无法证明修的是同一个问题。

**实证案例**：修复期多张票直接改代码，验证在事后补做。某票首版「修复」实际**引入回归**（有序列表数字消失 + 圆点覆盖任务标记）——若有先行的红/绿对照，该回归会在同一轮暴露。

**如何验证**：票上是否有修复前的失败输出（红）与修复后的通过输出（绿）成对出现。

---

### DQ-4 「flaky」必须给出机制解释，不得以重跑结案

**规则**：将失败判为「flaky」时，**必须给出「为何间歇」的机制解释**，而不能以「重跑通过」结案。特别地：**若测试吞掉断言失败（继续执行模式），flaky 可能掩盖确定性损坏**，此时必须逐步核对每个子步骤的结论。

**理由**：重跑通过只证明「这次没踩到」，不证明「行为正确」。若某失败的概率较高但非 100%，重跑会**系统性地放过**真实缺陷。

**实证案例**：`#187` 以「CI flaky，跨 PR 间歇复现」立项并长期挂着。真相是：测试步骤是**确定性失败**（陈旧断言必失败），它们吃掉约 25s 预算，使总时长落在边界区间 —— **恰好跨过超时线**，于是表现为「间歇」。**「flaky」这个标签主动掩盖了一个必然损坏的 spec**；且该 spec 用 `record()` 吞掉步骤失败，CI 只看退出码 → 步骤全挂也绿。

**如何验证**：flaky 票是否有机制解释段落；是否有「逐步核对各子步骤结论」而非仅「重跑 N 次通过」的证据。

---

### DQ-5 关闭缺陷须附验证者原始证据

**规则**：关闭缺陷票前，必须由**验证者（非修复者）**跑自己的探针，并把**原始输出**粘贴到票上。「测试通过」「已修复」「冒烟正常」是**结论不是证据**，不予采信。

**理由**：同 QG-5。缺陷场景下更严——因为「已修复」正是假修复的自报措辞。

**实证案例**：4 个假修复全部以「测试通过 / 已修复 / 冒烟通过 / 计数通过」自报完成，**4/4 全部由独立探针推翻**。

**如何验证**：票上是否存在验证者粘贴的原始输出块（标准输出 / DOM 快照 / 计算样式值 / 解析错误数）。

---

### DQ-6 同根因合并例外（1 bug = 1 PR 的合法豁免）

**规则**：默认 **1 bug 票 = 1 `fix/<slug>` 分支 = 1 PR**。**例外**：若 N 张票**同根因、同文件、同修复**，允许 1 PR 关闭 N 票——但 PR body 必须**逐票 `fixes #N`** 并**说明共同根因**，且各票需在评论中记录「已由 #PR 一并修复」。

**理由**：规则被合理违反时若没有豁免通道，执行者会**静默忽略规则**，从而侵蚀整条规则（含其真正该守的默认情形）。

**实证案例**：4 张同属「智能输入」、同一根因、同一文件的票由 1 个 PR 一并关闭。这是**合理**的，但规则现文无任何豁免条款——属于「规则与现实不符」。

**如何验证**：PR body 是否逐票 `fixes #N`；是否说明共同根因。

---

### DQ-7 多票同根因 → 必须升级为规范修订

**规则**：当 **≥3 张缺陷票**指向**同一流程环节**时，不得只逐票修复，必须**反查该流程环节并产出规范修订**（QG / DQ 条目或流程文档），在 change 或缺陷票上留痕。

**理由**：多票同源意味着缺陷来自**流程而非个体实现**。只修个例，同类问题会在下一个 change 复现。

**实证案例**：某 change 的 10 张缺陷票**全部**指向同一流程环节——「完成定义写在库层 + 无 e2e 绑定 + 接线无归属」。当时逐票修复（6 个 PR），**从未反查流程**，直到用户要求复盘才产出 QG-1..QG-7。若在**第 3 张票**时就反查，可提前拦截后续 7 张。

**如何验证**：是否产出了规范修订并能回溯到触发它的缺陷集合。

---

### DQ-8 生命周期标签维护

**规则**：缺陷票关闭时**必须移除进度类标签**（`needs-triage` / `ready-for-agent`），使标签与终态一致。P0/P1 票**部分交付**时，票**保持 OPEN** 并在票上评论**列出已交付增量与剩余项**。

**理由**：标签即状态机。关闭票残留 `ready-for-agent` 会污染 frontier 查询（`gh issue list --label ready-for-agent --state open`），而该查询正是 G3 自动推进的依据。

**实证案例**：一张 P0 票在子集交付后仍 `OPEN` 且带 `ready-for-agent`，与已关闭的同批票（同样残留该标签）混在同一标签集中；剩余增量仅靠人工评论记录。

**如何验证**：
```bash
gh issue list --label ready-for-agent --state all --json number,state \
  --jq '.[] | select(.state=="CLOSED") | .number'
# 期望：无输出（关闭票不应残留 ready-for-agent）
```

## 四、QG-1 的固定 AC 格式（三分类模板）

面向用户的票，AC 必须包含**三行**，分别对应存在 / 生命周期 / 保真（可直接复制，`<dev 命令>` 取 `.change-workflow.conf` 的 `CMD_*`）：

```
【存在】在 `<dev 命令>` 打开的页面中，<具体操作> 之后，<可观测到的元素出现>。
【生命周期】覆盖适用态：打开 / 切换 / 取消 / 外部点击 / 空态 / 关闭；取消后无残留（无残留文本 / 无残留浮层 / 无残留菜单）。
【保真】<关键文本/像素> 严格等于 <预期值>；<关键元素> 不含 <伪影文本>；验证：<E2E_DIR> 下对应 e2e 用例通过（含文本相等 / 状态往返 / 视觉探针断言）。
```

**反向验收判据**：若一条 AC 能在**不修改 `<APP_DIR>`** 的前提下被满足 → 说明票切错了（触发 QG-7）（发布前由 `cw-tickets-check.sh` 的 C3/C4/C8 机检兜底）。

## 五、QG-4 的代码对照（含断言阶梯与三条反例）

```ts
// ❌ 绕过 keymap 两跳，bug 恰好在那两跳
handleAutoPair(view, '**')

// ✅ 驱动真实输入路径
await view.dispatch(inputEvent(view, '**'))
```

同源补充规则：

- 测 DOM 可见性 → 必须断言**计算样式**，禁止断言「元素存在」
  ```ts
  // ❌ 元素存在即通过，但可能 opacity:0 不可见
  await expect(marker).toHaveCount(1)
  // ✅ 断言真实可见性
  expect(Number(await marker.evaluate((el) => getComputedStyle(el).opacity))).toBe(0)
  ```
- 测插件扩展 → 必须经**真实 `EditorView`**，禁止 mock `EditorState`
  - 依赖语法树解析的逻辑（如结构诊断）无法被 mock 对象满足，必须用真实实例
- **吞异常的测试（继续执行模式）** → 必须把累积失败在测试末尾**升级为测试失败**，否则 CI 退出码与测试结论脱钩
  ```ts
  // ❌ record() 吞掉断言失败以延续后续步骤 → 步骤全挂时测试仍「绿」，CI 只看退出码
  const record = async (name, fn) => { try { await fn() } catch (e) { steps[name] = { pass: false } } }
  // ✅ 末尾把累积失败升级为测试失败，使退出码与结论一致
  expect(Object.entries(steps).filter(([, s]) => !s.pass).map(([n]) => n)).toEqual([])
  ```

**断言强度阶梯对照**（渲染/浮层类 ≥ 文本相等；可取消类 ≥ 状态往返）：

```ts
// ❌ 仅存在性（层级 1）——渲染/浮层/可取消类违规
await expect(el).toHaveCount(1)

// ❌ 仅可见性（层级 2）——渲染/浮层/可取消类违规
expect(await el.evaluate(e => getComputedStyle(e).visibility)).not.toBe('hidden')

// ✅ 文本相等（层级 3）——渲染/装饰/插入/浮层类最低门槛
await expect(el).toHaveText('注释')

// ✅ 状态往返（层级 4）——可取消/可关闭交互最低门槛
await page.click('[data-testid=open]')
await expect(menu).toBeVisible()
await page.click('[data-testid=cancel]')
await expect(menu).toBeHidden()  // 回初始
await expect(input).not.toContainText('/')  // 无残留

// ✅ 视觉探针（层级 5）——关键交互流程
// 由 e2e 状态往返驱动产出 state-coverage.json + 多态截图
```

**三条正反例（editor-v2 实证 D2/D3/D6）**：

```ts
// D2 callout 标题重复「注释 注释」
// ❌ 仅断言 callout 存在
await expect(callout).toHaveCount(1)
// ✅ 文本相等：标头严格等于「注释」（不含重复）
await expect(calloutHeader).toHaveText('注释')

// D3 代码围栏残留反引号 `\`js`

// ✅ 保真：代码行不含反引号
await expect(codeBlock).not.toContainText('`js')

// D6 取消后 `/` 残留
// ❌ 仅断言菜单关闭

// ✅ 状态往返：取消后输入框无残留斜杠
await expect(editor).not.toContainText('/')
```

## 六、QG-5 的独立验证协议

验证者（orchestrator，非实施者）必须执行：

1. 读**实际 diff**，不只读报告
2. 跑**自己的探针**（不复用实施者的测试）
3. **把原始输出粘贴到票上**（原始 stdout / DOM 快照 / 计算样式值 / 解析错误数）
4. 标注**验证基于的 HEAD SHA**（`git rev-parse HEAD`，记作 `QG-5 验证基于 <sha>`）——rebase / 追加提交会使该结论过期，G2 的 `--verified-sha` 检查据此拦截
5. 未粘贴原始观察证据的「已完成」→ **不予采信**

**禁止采信的证据形式**：「测试通过」「已修复」「冒烟正常」——这些是**结论**，不是**证据**。

## 七、豁免机制

| 门禁 | 可否豁免 | 条件 |
|------|----------|------|
| QG-1 用户层 AC | ✅ | 票上显式标注 `no-ui-impact`（浮层/插入/渲染类**不得**豁免生命周期与保真 AC） |
| QG-2 e2e 绑定 | ✅ | 票上显式标注 `no-ui-impact` |
| QG-3 接线归属 | ❌ | 不可豁免 |
| QG-4 真实路径测试 | ❌ | 不可豁免 |
| QG-5 独立验证 | ❌ | 不可豁免 |
| QG-6 集成 checkpoint | ✅ | 票数 < 6 时自然不适用 |
| QG-7 纵向切片 | ❌ | 不可豁免 |
| QG-8 发现闭环门 | ❌ | 不可豁免 |
| DQ-1 triage 不可跳过 | ❌ | 不可豁免 |
| DQ-2 根因独立确认 | ❌ | 不可豁免 |
| DQ-3 先红后绿 | ❌ | 不可豁免（紧急 P0 可事后补，但须在票上留痕） |
| DQ-4 flaky 机制解释 | ❌ | 不可豁免 |
| DQ-5 关闭附原始证据 | ❌ | 不可豁免 |
| DQ-6 同根因合并 | ✅ | 本条目自身即豁免条款 |
| DQ-7 多票升级规范 | ✅ | 票数 < 3 时自然不适用 |
| DQ-8 标签维护 | ❌ | 不可豁免 |

**适用 `no-ui-impact` 的票型**：纯重构、纯库内改动、纯文档、纯基建。

**收紧 `no-ui-impact`**：浮层 / 插入 / 渲染类变更**不得**以 `no-ui-impact` 豁免生命周期与保真 AC（QG-1 第②③类）。此类变更本质上是用户可见交互，必须覆盖六态生命周期与保真文本/像素判据。

**豁免必须由票的作者显式声明，不得默认**。未声明即视为需要遵守 QG-1/QG-2。

**引用纪律**：本次应用或豁免的每条 QG/DQ，必须在 PR body 逐条写出 `QG-x / DQ-x: <它改变了哪个具体决策>`（例：`QG-5: 用真实按键探针替代测试摘要`）；只提编号、不写决策 = **空引用**，视同未声明，**不予合并**。

## 八、减法审计（防 process rot）

### 规则

每个季度（或每完成一个 ≥6 票的 change 收口后）执行一次**减法审计**：

1. **统计三指标**：逐条统计 QG/DQ 的——**执行率**（该门禁适用的票中实际执行的比例）、**阻断数**（该门禁拦截的真实违规数）、**下游归因缺陷数**（应拦未拦、在下游暴露的缺陷数）。数据来源：缺陷票的规范修订归因（DQ-7——≥3 票同源说明该环节判据缺席或失效）、fix-first 自愈回路的触发记录、e2e/CI/独立探针的拦截记录。**单一「捕获次数」不足**：高执行、零阻断、零下游事故恰是**执行得最好**的门禁（合规率高），会被「零捕获」误退役。
2. **填「门禁捕获统计」表**（记录在 CHANGELOG、复盘文档或缺陷票上）：

   | 门禁 | 本周期捕获数 | 最近捕获来源（票号 / PR） | 判定 | expected capture（预期捕获场景） |
   |---|---|---|---|---|
   | QG-1 | — | — | 保留 | callout 重复 / 围栏反引号 / 取消残留 / 仅存在性 AC |
   | QG-4 | — | — | 保留 | 存在性断言冒充可见变更 / 可取消交互无往返断言 |
   | QG-5 | 5 | 缺陷修复期 4 个假修复被独立探针推翻；#556 收口子集验证漏跑 test_v2_matcher | 保留 | 单层截图冒充交互票证据 / 伪造手动 QA / 元素存在自证 / 收口子集验证冒充全链验证 |
   | QG-6 | 0 | — | 提案合并 / 退役 | — |
   | QG-8 | — | — | 保留 | findings 未转 issue / 规格条目 |

   **机制层机检的 expected capture**（v1.10.0 新增，供三指标对账）：
   | 机制 | expected capture（预期捕获场景） |
   |---|---|
   | 锚点门（`conformance.json` 四项机检） | 规格无锚点 / 锚点不可断言 / 来源缺失（规格不明确） |
   | 一致性制品 baseline 哈希锁 | baseline 被改 / 制品缺失 |
   | 证据 manifest（ui-surface 票） | 零产物（如消费仓 #327–#336）/ 散文冒充证据 |
   | CI 三层核验（T1/T2/T3） | 图标名 / 几何 / 色值偏离 / 视觉不符 / 状态残留 |
   | exit-3 降级理由收紧 | 无正当理由跳证据（headless 洗白） |

3. **三指标处置**：连续两个审计周期**高执行 + 零阻断 + 零下游事故**的门禁 → 提出**合并**（并入相邻判据）或**退役**（删除条目）；退役须留痕（CHANGELOG / 复盘），附三指标数据——不得凭印象删除。**关键词型门禁**（每次命中文本但不拦真实缺陷，如仅 grep AC 关键词）须按「高捕获、零预防价值」识别，提出合并 / 退役。
4. **最小充分集保护**：审计结论不得削弱最小充分集（§九）——QG-1+QG-2+QG-5 与 DQ-1+DQ-3+DQ-5 永不因「零捕获」退役：它们多为兜底判据，零捕获恰恰可能是其它门禁在更早环节已经拦住。

### 理由

门禁天生只增不减：每次事故复盘倾向于「加一条规则」，而没有任何环节会问「哪条规则其实从未抓到东西」。规则数量超过执行者的注意力容量后，**执行率被稀释**——门禁退化为仪式，并制造「有门禁在把关」的虚假安全感。减法审计把「删除」也变成需要证据的决策，与「加规则」对等。

### 实证案例

本规范的源项目经验：门禁从六条最小充分集扩展到 15 条、编排文件逐版增长，全程无人统计过其中哪条真的拦下过交付；直到一次「agent 记不住全部规则」的复盘才暴露——失效不是某条规则写错了，而是**规则总量从未被管理**。

### 如何验证

- 审计记录存在，且每条退役/合并决定都能回溯到对应的零捕获数据
- 无「凭印象删除」：所有删除都附有统计表或缺陷票归因
- 新增/修订门禁均有 expected capture 行，下一季度对账
