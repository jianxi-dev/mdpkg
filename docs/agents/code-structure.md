# 服务层架构约束

> 适用范围：G1 实施阶段中涉及共享操作逻辑的变更；G1 出口 `code-review` 的 Standards 轴对照项。
> 生效日期：2026-09-20
> 配套：`docs/agents/quality-gates.md`（票内容与完成判据）、`.opencode/skills/change-workflow/SKILL.md`（G0-G4 gate 编排）

---

## 一、两层分离定义

本规范的核心是**编排层**与**服务层**的职责切分：

- **actions（编排层）管 why/when**：决定何时做、为何做、串联流程；持有业务规则、状态转换、权限与归属校验、失败分类、重试策略、面向用户的错误。
- **service layer（服务层）管 how**：集中可复用的操作机制，显式入参、结构化返回、不直连 DB、失败显式。

经验法则是：**"这个产品流程意味着什么"** 留在 actions；**"如何可靠地完成这个操作"** 下沉到 service。

---

## 二、服务函数特征

每个 service 函数应满足以下四条：

1. **显式参数**：所需数据全部由调用方经参数传入，不依赖隐式全局状态或闭包捕获。
2. **结构化返回**：返回值形状固定（如 `{ ok, value }` / `{ ready, previewUrl }`），调用方按字段解构，不靠副作用读取结果。
3. **不直连 DB**：service 不直接读写数据库表；持久化由 actions 或更上层协调，service 只负责单次操作的原子机制。
4. **失败显式**：错误通过返回值或抛出向上传播，禁止 `catch {}` 吞掉后返回 `undefined` / `null` 伪装成功。

## 三、反模式清单

### God service

- **症状**：单个 service 文件/函数承载所有控制流，调用方只需传一个 `mode` 参数。
- **后果**：任何改动都影响全部调用方；回归面无限扩大；测试必须覆盖所有分支组合。
- **修复**：按能力拆分为多个 composable 函数（如 `createSandbox` / `installDeps` / `startRuntime`），让调用方自选组合。

### Leaky service

- **症状**：service 内部直接写入数据库表、修改 domain 状态、或调用本属于 actions 的权限校验。
- **后果**：绕过编排层的业务规则；同一操作在不同调用方下产生不一致的副作用；回滚困难。
- **修复**：把状态变更收回到 actions；service 只返回"做了什么"的凭证，由 actions 决定何时落库。

### Inconsistent API

- **症状**：同一 service 文件内，各函数的参数顺序、错误语义、返回形状各不相同（有的抛错、有的返回 `{ error }`、有的回调）。
- **后果**：调用方无法建立统一错误处理；新人阅读成本陡增；复制粘贴时易出错。
- **修复**：选定一种约定（推荐"结构化返回 + 显式 throw"），全文件统一；旧函数标记废弃并逐步迁移。

### Over-abstraction

- **症状**：仅被一处使用的逻辑被抽成 service，或把领域特定的业务规则下沉到"共享"层。
- **后果**：增加间接层却不带来复用；修改时要在两个文件间跳转；实际只有一条调用链。
- **修复**：先写在 actions 里，等出现**第二个真实调用方**再抽取；抽取时只抽非领域块，领域策略留在 actions。

## 四、迁移清单

安全抽取共享逻辑的顺序：

1. **先写 action**：在 action 代码中把流程写清楚，行为明确后再找重复。
2. **标出重复块**：跨 2+ 调用方出现的非领域操作块做标记（注释 `// CANDIDATE: shared`）。
3. **只抽非领域块**：把标记的重复操作下沉到 service；领域策略（auth、状态转换、错误分类）留在 actions。
4. **替换一处并验证**：先改一个调用方，跑 typecheck / lint / 测试，确认行为一致。
5. **再替换其余**：逐处迁移，每处都验证；禁止一次性全改。

---

## 五、挂载点

本规范在以下两处生效：

- **G1 实施（`implement`）**：实施阶段若引入共享操作逻辑，按§二、§三自检。
- **G1 出口（`code-review` 的 Standards 轴）**：自审时对照§三反模式清单；命中任一条须回修，不回修须在票上显式说明理由（如"当前仅单调用方，暂不抽取"）。

---

## 六、备注

本规范是**架构对照检查项**，不是强制所有改动都过。仅在本次 diff 含以下特征时触发：

- 新增共享操作逻辑（service / helper / util）；
- 跨 2+ 流程出现重复块；
- 已有 service 的 API 形状发生变更。

纯前端样式调整、单调用方内部重构、文档或配置变更不强制套用本规范。
